# Linux Special Permission Bits – Lab 04 Notes

## Objective

The purpose of this lab was to understand Linux **special permission bits** — SUID, SGID, and the sticky bit — and analyze their behavior from both **security** and **attacker** perspectives.

---

## 1. SUID (Set User ID)

### Description

SUID allows a program to execute with the privileges of the **file owner** instead of the user running it. This mechanism is commonly used by system utilities that require elevated privileges.

### Lab Implementation

A Python script was created to display the real and effective user IDs using:

```python
import os
print("Real UID:", os.getuid())
print("Effective UID:", os.geteuid())
```

The script was made executable, owned by root, and assigned the SUID permission.

### Behavior Observed

When executed as a normal user:

* The real UID remained unchanged
* The effective UID did **not** change to root

### Explanation

Linux intentionally ignores SUID on interpreted scripts (Python, Bash) for security reasons. Only **compiled binaries** can safely use SUID. This prevents race conditions and interpreter‑based privilege escalation.

### Security Insight

Misconfigured SUID binaries are a major privilege escalation vector. Attackers enumerate them using:

```bash
find / -perm -4000 -type f 2>/dev/null
```

---

## 2. SGID (Set Group ID)

### Description

SGID on a directory ensures that all newly created files inherit the **group ownership** of the directory rather than the creator’s primary group.

### Lab Implementation

A shared directory was created with group ownership set to `redteam` and SGID enabled:

```bash
chmod 2775 shared
```

### Behavior Observed

Files created inside the directory automatically inherited the `redteam` group.

### Security Insight

SGID is commonly used in shared environments such as:

* Web server directories
* Development team folders

If a group‑writable SGID directory contains executable scripts or sensitive files, it can be abused for:

* Code injection
* Persistence
* Privilege escalation

---

## 3. Sticky Bit

### Description

The sticky bit restricts file deletion in world‑writable directories. Only the **file owner** or root can delete or rename files.

### Lab Implementation

A directory was created with full permissions and the sticky bit was applied:

```bash
chmod +t testtmp
```

Directory permissions changed to:

```
drwxrwxrwt
```

### Behavior Observed

* All users could create files
* Only file owners could delete their own files

### Security Insight

The sticky bit is critical for directories like `/tmp`. Without it:

* Users could delete or replace others’ files
* This could lead to denial‑of‑service or symlink attacks

---

## Key Takeaways

* SUID, SGID, and sticky bits are powerful and dangerous if misconfigured
* These permissions are frequent targets for attackers
* Proper configuration is essential for system security and hardening

This lab demonstrated how Linux special permission bits function and how they can become attack vectors if improperly managed. Understanding these mechanisms is essential for both defensive security and penetration testing.
